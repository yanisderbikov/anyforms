# anyforms
backend for anyforms.ru

## Вход в админку и выдача доступов

Паролей нет: вход по одноразовому коду из письма (NotiSend). Пользователи админки живут в таблице `users`
(`email`, `name`, `role`), заводит их супер-админ на скрытой странице `/admin/users`.

- **Супер-админ** — почта из env `ADMIN_SUPER_EMAIL` (обязательная, без дефолта). Запись в `users`
  создаётся сама при первом входе (роль `ADMIN`). Только он видит `/admin/users` и может дёргать
  `/api/admin-users/**` (authority `ROLE_SUPER_ADMIN` выдаёт `JwtAuthFilter` по совпадению почты с env).
  Удалить его или сменить ему роль нельзя.
- Роль пользователя фильтр берёт **из БД, а не из JWT** (`UserAccessService`): результат кешируется на 5 минут
  по почте, а выдача, смена роли и отзыв в `/admin/users` сбрасывают запись из кеша, поэтому действуют сразу.
  В JWT роль и флаг `super` лежат только для меню фронта.
- Роли админки: `ADMIN`, `SALES_MANAGER`, `PROJECT_MANAGER` (check-constraint в V57).

| Метод и путь | Что делает |
|---|---|
| `POST /api/auth/request-code` `{email}` | шлёт 6-значный код на почту; 403 — доступ не выдан, 429 — код уже отправлен меньше минуты назад, 502 — письмо не ушло |
| `POST /api/auth/verify-code` `{email, code}` | проверяет код → `{token}` (JWT). Код живёт `auth.login-code.ttl-minutes` (10 мин), 5 неверных попыток — код сгорает |
| `GET /api/auth/me` | почта, имя, роль и флаг `superAdmin` из БД; фронт строит по ним меню при каждой загрузке админки, 401 — доступ отозван |
| `GET /api/admin-users` | все пользователи админки |
| `POST /api/admin-users` `{email, name, role}` | выдать доступ; 409 — уже выдан |
| `PUT /api/admin-users/{id}` `{name, role}` | сменить имя/роль |
| `DELETE /api/admin-users/{id}` | отозвать доступ |

В БД хранится только SHA-256 кода (`login_code_hash`), сам код — только в письме. Миграция `V57__email_login.sql`
удалила всех старых пользователей с паролями.

## Salesbot drip-кампания (триггер SalesBot по расписанию)

Сервис по расписанию запускает SalesBot'ы в amoCRM для сделок (лидов) в заданном
статусе воронки. На каждом слоте расписания лиду уезжает следующий по порядку бот.
Пока лид в целевом статусе — цепочка идёт; ответил клиент → amoCRM переносит сделку в
другой статус → лид выпадает из выборки и боты больше не уходят.

### Схема БД

Таблицы создаёт **Flyway** (`src/main/resources/db/migration/`):
- `V1__init_salesbot_schema.sql` — исходная схема (4 таблицы);
- `V2__salesbot_refinements.sql` — `schedule.time_utc` → `timestamptz` (под `Instant`) + сид расписания.

| Таблица | Назначение | Кто заполняет |
|---|---|---|
| `bot_group` | группа цепочки: название, воронка/статус amoCRM, вкл/выкл (с V52; заменила `order_type_funnel` и типы заказа) | **админка** `/admin/salesbot` |
| `bot_sequence` | порядок ботов в группе (`group_id`, `position`) | **админка** `/admin/salesbot` |
| `bot_group_lead_seen` | когда сделка впервые замечена в статусе группы (якорь задержки шага 1) | **приложение само** |
| `bot_execution_log` | журнал отправок (источник истины о прогрессе) | **приложение само**; смотреть — `/admin/salesbot/analytics` |

### Админка (только ADMIN): `/api/salesbot/admin/**`

Фронт: раздел «боты amocrm» в админке (`/admin/salesbot` — цепочки, `/admin/salesbot/analytics` — аналитика и журнал).
Все ручки под `/api/salesbot/**` требуют роль `ADMIN` (включая ручной запуск `POST /api/salesbot/run-batch`).

| Метод и путь | Что делает |
|---|---|
| `GET /api/salesbot/admin/run-types` | справочник типов записей журнала: `DRIP` (шаг цепочки группы), `MANUAL`, `DELIVERY` |
| `GET /api/salesbot/admin/bots?refresh=` | SalesBot'ы аккаунта из amoCRM (`GET /api/v4/bots`, кэш 5 мин) — в админке бот выбирается по имени, в таблицу пишется `id` |
| `GET /api/salesbot/admin/pipelines?refresh=` | воронки и статусы аккаунта (`GET /api/v4/leads/pipelines`, кэш 5 мин) — выбор по имени, хранятся id |
| `GET /api/salesbot/admin/groups` | группы дрип-кампании (`bot_group`) с цепочками (`bot_sequence`) |
| `POST/PUT/DELETE /api/salesbot/admin/groups[/{id}]` | группа: название, воронка/статус (парой или пусто), вкл/выкл, окно отправки `sendFrom`/`sendTo` (HH:mm по Москве, парой или пусто); удаление сносит цепочку, журнал остаётся без ссылки |
| `POST /api/salesbot/admin/steps` `{groupId, botId, delayMinutes}` | бот добавляется **в конец** цепочки группы (позиция = последняя + 1); один бот — не более одного раза на группу |
| `PUT /api/salesbot/admin/steps/{id}` `{botId, delayMinutes}` | заменить бота/задержку на шаге, позиция не меняется |
| `POST /api/salesbot/admin/steps/{id}/move?direction=UP\|DOWN` | поменять шаг местами с соседним (порядок только стрелками, руками позиция не задаётся) |
| `DELETE /api/salesbot/admin/steps/{id}` | удалить шаг; позиции остальных не сдвигаются (пропуски допустимы) |
| `GET /api/salesbot/admin/manual-runs` | последние ручные запуски с живыми счётчиками (в памяти процесса) |
| `GET /api/salesbot/admin/manual-runs/preview?pipelineId&statusId&botId&tagName&retail` | сколько лидов в статусе и сколько уже получали бота; `botId` необязателен; `retail=true/false` — фильтр по полю сделки «Розница» |
| `POST /api/salesbot/admin/manual-runs` `{pipelineId, statusId, botId, tagName?, retail?}` | запустить бота всем лидам воронки/статуса в фоне (202); один запуск за раз (409) |
| `GET /api/salesbot/admin/analytics?from&to` | счётчики `SUCCESS` / `MESSAGE_SEND_FAILED` / `FAILED` по каждому шагу — видно, после какого бота сообщения перестают доставляться; даты — дни по МСК, включительно |
| `GET /api/salesbot/admin/logs?type&groupId&status&leadId&from&to&page&size` | журнал `bot_execution_log` постранично, новые сверху |

> Прогресс лида считается **по позициям**. Перестановка шагов меняет порядок и для лидов в работе,
> но один и тот же бот одному лиду повторно не уходит: прогон проверяет журнал
> (`BotExecutionReader.alreadyExecuted`) и уже отправленного бота засчитывает без повторной отправки.

> Все времена в БД — в **UTC**. МСК = UTC+3 (без перехода на лето).
> С V52 цепочки привязаны к группам (`bot_group`), а не к типам заказа. В журнале `type` — enum `BotRunType`: `DRIP` (шаг цепочки, `group_id` задан), `MANUAL`, `DELIVERY`.

---

### 1. `bot_group` — группы: название + где искать лидов

Одна строка = одна группа дрип-кампании. Заводится и правится в админке `/admin/salesbot`
(«боты amocrm → цепочки»): название, воронка/статус amoCRM (выбираются по имени, хранятся id),
пауза (`enabled`). Шедулер обрабатывает только включённые группы с заданной воронкой и статусом.

| Колонка | Смысл |
|---|---|
| `name` | название группы (любое, для людей) |
| `pipeline_id` / `status_id` | где искать лидов; оба `NULL` — группа не обрабатывается |
| `enabled` | `FALSE` — пауза: настройки и цепочка остаются, боты не уходят |

---

### 2. `bot_sequence` — цепочка ботов группы

Одна строка = один бот на одной позиции в группе (`group_id`). Ботов добавляют в конец
(позиция = последняя + 1), порядок меняют стрелками (обмен позициями с соседом), руками
позиция не задаётся. Один бот — не более одного раза на группу.

- `UNIQUE(group_id, position)` — позиции в группе не повторяются; пропуски после удаления допустимы.
- На каждом слоте лиду уезжает **первая позиция без записи `SUCCESS`** в журнале (в рамках группы).
- Один и тот же бот одному лиду повторно не уходит даже после перестановки: прогон проверяет
  журнал и уже отправленного бота засчитывает без повторной отправки.

---

### 3. Когда запускать: регулярный прогон + задержки шагов

Таблицы `schedule` больше нет (V53). Прогон проверяет лидов каждые `salesbot.run.interval-minutes`
минут круглосуточно. Когда именно уходят боты, задают две настройки. Окно отправки группы
(`bot_group.send_from`/`send_to` — timestamptz как Instant, дата-плейсхолдер 1970-01-01, значимо время суток по Москве; пусто — `salesbot.run.window-msk`): если срок шага выпал
вне окна, бот уходит при следующем открытии окна. И задержки шагов:
у каждого `delay_minutes` — «не раньше чем через N минут после предыдущего шага»; для первого
шага отсчёт от момента, когда прогон впервые увидел сделку в статусе группы
(`bot_group_lead_seen`, пишется один раз на пару группа/сделка). В админке задержка вводится
как дни + часы. Так у разных групп разный ритм, и сообщения не уходят всем в одно время.

---

### 4. `bot_execution_log` — заполняется автоматически, руками не трогать

Ведёт приложение. Источник истины о прогрессе цепочки — по нему вычисляется
«следующий бот». Только для чтения/диагностики.

| Колонка | Смысл |
|---|---|
| `lead_id` | сделка amoCRM |
| `bot_id` / `position` / `type` | какой бот / позиция / тип отработали |
| `status` | `SUCCESS` (запрос на запуск ушёл), `FAILED` (лид вышел из статуса / ошибка запроса) или `MESSAGE_SEND_FAILED` (бот запущен, но amoCRM не доставил сообщение — вебхук `fail-send-message`; ставится на последнюю запись лида) |
| `date_executed` | момент попытки (`timestamptz`, UTC) |

- `UNIQUE(lead_id, bot_id)` — жёсткий бэкстоп от двойной отправки; запись через upsert.
- Прогресс = **первая позиция без `SUCCESS`**. `FAILED` прогресс не двигает (может позже
  «повыситься» до `SUCCESS`). Вся цепочка в `SUCCESS` → лиду больше ничего не шлётся.

---

### Минимальный чек-лист запуска

1. Создать группы и задать им воронку/статус — в админке `/admin/salesbot`.
2. Собрать цепочки ботов групп — там же.
3. Проверить `salesbot.run.*` (интервал и окно прогона) и задержки шагов в группах.
4. `bot_execution_log` оставить пустым — заполнится сам.

### Конфигурация (`application.properties`)

| Свойство | Назначение |
|---|---|
| `salesbot.scheduler.enabled` | вкл/выкл тикер |
| `salesbot.scheduler.tick-ms` | период тика, мс |
| `salesbot.run.interval-minutes` | как часто проверять лидов (мин), круглосуточно |
| `salesbot.run.window-msk` | окно отправки по умолчанию для групп без своего, Москва, `HH:mm-HH:mm` |
| `salesbot.lock.key` | ключ Postgres advisory-lock (single-flight: один прогон одновременно во всём кластере) |

> Сборка — только под **JDK 21** (дефолтный `mvn` на JDK 25 ломает Lombok).
